# Invoicey — Indian invoicing compliance & usability research (2026)

Researched 2026-08-17. Sources cited inline. Anything I could not confirm from a
primary/authoritative source is marked **UNVERIFIED**.

Severity legend:
- **BLOCKER** — invoices the app produces are legally wrong or unusable for the target user.
- **HIGH** — usable but the user will hit a wall fast, or has to hand-edit every invoice.
- **NICE-TO-HAVE** — polish / differentiation.

Sizing: **S** ≈ a field + a render line; **M** ≈ schema + form + preview + export + API normalize;
**L** ≈ new document type, new derivation engine, or external integration.

## 0. Baseline — what Invoicey actually is today

Read from source, not assumed.

`models/Invoice.ts` (whole schema):
`userId, companyName, companyEmail?, companyPhone?, companyAddress?, companyLogo?,
billTo, billToEmail?, billToAddress?, invoiceNumber, invoiceDate, dueDate, terms?,
notes?, currency (default "INR"), items[{name, price, quantity}], subtotal, discount,
tax? (legacy), cgst, sgst, convenienceCharge, paymentInfo?, total,
status ("draft"|"sent"|"paid"|"overdue"), is_deleted, createdAt`.

Money formula, `lib/invoice-domain.ts:55` `computeTotals`:
`subtotal − discount + cgst + sgst + convenienceCharge`, clamped at 0, each step `round2`.
`buildTotalsRows` emits exactly: Subtotal, Discount, CGST, SGST, Service Charge, Total.

The export template `lib/invoice-export.ts` prints: logo, company name/address/email/phone,
"Bill From"/"Bill To" blocks, invoice number, invoice date, due date, a status pill, and an
item table with columns `# | Description | Qty | Unit Price | Amount`, then the totals rows,
then Terms / Payment Information / Additional Notes, then a "Generated by Invoicey" footer.

Formatting: `formatCurrency` uses `en-IN` **only when currency === "INR"** (so grouping is
correct for INR), `formatDateLong` uses **`en-US`** — `"Aug 17, 2026"` — for every locale.

**The five structural facts that drive almost every finding below:**
1. There is **no GSTIN field** anywhere — not for the supplier, not for the recipient.
2. There is **no state / place-of-supply field** anywhere.
3. Tax is **two flat invoice-level rupee amounts** (`cgst`, `sgst`). There is no tax rate,
   no per-line tax, and **no IGST field at all**.
4. There is **no HSN/SAC, no unit of measure (UQC)** on a line item — a line is
   `{name, price, quantity}`.
5. There is **no document-type concept** — every document is titled hardcoded `INVOICE`
   in the export template (`<h1>INVOICE</h1>`), and the word "Tax Invoice" never appears.

## 1. Mandatory tax-invoice fields (CGST Rule 46)

**(a) What the law requires.** Rule 46 of the CGST Rules, 2017 lists the particulars a
tax invoice issued by a registered person must contain. Clause by clause:

| Rule 46 clause | Particular | In Invoicey? |
|---|---|---|
| (a) | Name, address and **GSTIN of the supplier** | name/address yes, **GSTIN no** |
| (b) | **Consecutive serial number**, max **16 characters**, one or multiple series, unique for the financial year | free-text, unvalidated |
| (c) | **Date of issue** | yes (`invoiceDate`) |
| (d) | Name, address and **GSTIN/UIN of the recipient**, if registered | name/address yes, **GSTIN no** |
| (e) | For an **unregistered** recipient where taxable value ≥ **₹50,000**: name, address, **delivery address, State name and State code** | no |
| (f) | **HSN code of goods / SAC of services** | no |
| (g) | **Description** of goods or services | yes (`items[].name`) |
| (h) | **Quantity** and **unit / Unique Quantity Code (UQC)** | quantity yes, **unit no** |
| (i) | **Total value** of supply | yes (`subtotal`) |
| (j) | **Taxable value** after discount/abatement | discount is invoice-level only |
| (k) | **Rate of tax** (CGST, SGST, IGST, UTGST, cess) | **no rate anywhere** |
| (l) | **Amount of tax charged**, split by CGST/SGST/IGST/UTGST/cess | CGST+SGST amounts only, **no IGST** |
| (m) | **Place of supply** along with the **name of the State**, for inter-State supply | **no** |
| (n) | **Address of delivery** where it differs from the place of supply | no |
| (o) | Whether tax is payable on **reverse charge** basis | **no** |
| (p)/(q) | **Signature or digital signature** of the supplier / authorised representative | no |
| (r) | **QR code** carrying the embedded IRN, where notified | no |

Two provisos that matter for a small-business product:
- **Signature waiver:** an invoice issued electronically in accordance with the
  Information Technology Act, 2000 (i.e. carrying a valid digital signature under that
  Act) does **not** require a physical/handwritten signature. A plain PDF emailed to a
  client is *not* IT-Act-signed, so in practice virtually every small vendor prints a
  signature block or the line **"This is a computer-generated invoice and does not
  require a signature."** That line is convention, widely accepted, not a statutory
  safe harbour — treat it as convention. (UNVERIFIED as a formal exemption; verified only
  as ubiquitous practice.)
- **Sub-₹50,000 unregistered recipient:** the recipient's details need be recorded only
  **on request**. So a B2C receipt for a small amount can legitimately be thin.

Serial number, **exactly what is allowed** (Rule 46(b) wording): a consecutive serial
number *not exceeding sixteen characters*, in one or multiple series, containing
**alphabets or numerals or the special characters hyphen/dash "-" and slash "/"**, and any
combination thereof, **unique for a financial year**. Nothing else is permitted — no `#`,
no spaces, no `_`, no `.`. Practical consequence: `INV/2026-27/001` (15 chars) is valid;
`INV #001` is not; `INV_001` is not.

**HSN/SAC digit requirement (turnover-based), current position:**
- Aggregate turnover in the preceding FY **up to ₹5 crore** → **4 digits**, mandatory on
  **B2B** invoices; optional on B2C.
- Aggregate turnover **above ₹5 crore** → **6 digits**, mandatory on **all** invoices.
- (Historic slabs — 2 digits under ₹1.5cr etc. — were superseded by Notification
  78/2020-CT w.e.f. 01.04.2021. Do not implement the old slabs.)
- E-invoices for AATO ≥ ₹5 crore have required 6-digit HSN since 15 Dec 2023.
- 8 digits are required for a notified list of chemicals/specified goods. Services use
  **SAC**, which is 6 digits and always begins `99` (e.g. `998314` IT consulting,
  `998313` management consulting, `998311` — freelancers overwhelmingly use `9983xx`
  or `9982xx`/`99839x`).

**(b) What Invoicey has.** Company name/address/email/phone, client name/address/email,
invoice number (free text), invoice date, due date, `{name, price, quantity}` line items,
one invoice-level discount, two invoice-level tax amounts, terms/notes/paymentInfo.
The export prints a hardcoded `INVOICE` title.

**(c) The concrete gap.** An invoice produced by Invoicey today is **missing 8 of the 16
Rule 46 particulars** for a GST-registered supplier: both GSTINs, HSN/SAC, unit, tax rate,
per-line taxable value, place of supply, reverse-charge indicator, and the signature block.
A registered user cannot legally issue it, and their client's accountant will bounce it
because there is no GSTIN to claim input tax credit against. **BLOCKER.**

**(d) Implementation sketch.**

```
  price: number,           // existing (unit price)
```

*Document header* — **S**

```
placeOfSupply?: string       // GST state code + name

```
The export's `<h1>INVOICE</h1>` must become `<h1>${DOCUMENT_TITLES[documentType]}</h1>`
— "TAX INVOICE" is the required heading for a registered supply, and using it when you

*Validation, in `validateInvoice`* — **S**

  "Invoice number must be at most 16 characters and use only letters, numbers, - and /".
- If `documentType === "tax_invoice"`: require `companyGstin`, require `placeOfSupply`,
  and require every line to have `hsnSac` and a `taxRatePercent`.

## 2. CGST/SGST vs IGST vs UTGST — the central defect

**This is the section that matters most. Invoicey cannot produce a correct inter-State
invoice, and it has no way of even knowing that an invoice is inter-State.**

### (a) What the law requires

GST is a *destination* tax split into two families, and which family applies is not a user
preference — it is **derived** from two facts:

1. **Location of the supplier** (the State of the supplier's GST registration).
2. **Place of supply** (POS), determined by IGST Act §10–13.

Then:

| Condition | Tax charged |
|---|---|
| Supplier State == POS State, both are States | **CGST + SGST**, each at half the total rate |
| Supplier State == POS, and it is a **Union Territory without a legislature** | **CGST + UTGST** |
| Supplier State != POS State | **IGST**, at the **full** rate |
| Supply to/by an **SEZ** unit or developer | **always IGST** (deemed inter-State even within the same State — IGST §7(5)/§8(1) proviso) |
| **Export** of goods/services (recipient outside India, POS outside India, payment in convertible forex, not the same legal person) | **zero-rated** (IGST §16): either IGST with refund, or **no tax under LUT/Bond** |
| Import of services | IGST under reverse charge, recipient pays |

Statutory hooks: IGST §7 (inter-State supply), §8 (intra-State supply, with the proviso
that an intra-State supply **excludes** supplies to or by an SEZ), §5 (levy of IGST),
§16 (zero-rated supply), and UTGST Act for UTGST.

**Determining the place of supply — the subset a freelancer/small-firm app needs:**

*Services, both parties in India (IGST §12):*
- **§12(2) default:**
  - Recipient is **GST-registered** → POS = **location of the recipient** (their GSTIN's State).
  - Recipient is **unregistered** → POS = the **address on record** with the supplier, and
    where no address is on record → **the location of the supplier**.
- Named exceptions that override §12(2) and that a small-business app should at least
  expose as a manual override:
  - §12(3) services **directly in relation to immovable property** (architects, interior
    designers, hotel accommodation, construction) → **location of the property**.
  - §12(4) restaurant, catering, personal grooming, fitness, beauty, health → **where
    performed**.
  - §12(5) **training and performance appraisal** → registered recipient: recipient's
    location; unregistered: where performed.
  - §12(6) **admission to an event/amusement park** → where the event is held.
  - §12(7) **organising an event**; §12(8) transportation of goods; §12(9) passenger
    transport; §12(11) telecom; §12(12) banking/financial; §12(13) insurance;
    §12(14) advertisement to government (apportioned by State).

*Goods, both parties in India (IGST §10):* POS is generally **where the movement of goods
terminates for delivery to the recipient**; for a "bill-to ship-to" transaction the POS is
deemed the **principal place of business of the third person** who directed the delivery.

*Recipient outside India (IGST §13):* default POS = **location of the recipient**; so an
Indian freelancer billing a US client normally has POS outside India → export of services →
**zero-rated**. Exceptions in §13(3)–(13) (performance-based services, immovable property,
intermediary services — an **intermediary**'s POS is the supplier's own location, which
turns what looks like an export into a taxable domestic supply; this is the single most
common trap for Indian agencies and consultants).

**Export invoice mandatory endorsement (Rule 46 proviso).** An export/SEZ invoice must
carry, verbatim, one of:
- `"SUPPLY MEANT FOR EXPORT/SUPPLY TO SEZ UNIT OR SEZ DEVELOPER FOR AUTHORISED OPERATIONS ON PAYMENT OF INTEGRATED TAX"`, or
- `"SUPPLY MEANT FOR EXPORT/SUPPLY TO SEZ UNIT OR SEZ DEVELOPER FOR AUTHORISED OPERATIONS UNDER BOND OR LETTER OF UNDERTAKING WITHOUT PAYMENT OF INTEGRATED TAX"`

and, in lieu of the domestic recipient particulars, must contain: **name and address of the
recipient, address of delivery, and name of the country of destination.** An LUT is valid
for **one financial year (Apr–Mar)** and must be re-filed each year; practice is to print
the **LUT ARN** on the invoice.

### (b) What Invoicey has

Two flat, invoice-level rupee amounts, `cgst` and `sgst`, typed in by hand (with a
UI-only %/₹ toggle whose percentage is never persisted). There is no supplier State, no
recipient State, no place of supply, no SEZ or export flag, **and no IGST field in the
schema, in `computeTotals`, in `buildTotalsRows`, in the AI contract, or in the export.**

### (c) The concrete gap — **BLOCKER**

1. **Every inter-State invoice Invoicey produces is legally wrong.** A Bengaluru
   freelancer billing a Mumbai client must charge 18% IGST. Invoicey can only offer them
   CGST 9% + SGST 9%. The recipient cannot claim input tax credit against a wrongly-headed
   tax, the supplier has under-reported IGST and over-reported CGST/SGST in GSTR-1/3B, and
   fixing it means a credit note plus a fresh invoice.
2. This is the *majority* case for the stated target user. A solo consultant's client list
   is nationwide; intra-State billing is the minority.
3. **Exports are also wrong.** PRODUCT.md explicitly supports USD/EUR/GBP/AED and says the
   user "occasionally invoices overseas". Such an invoice must be zero-rated with the
   statutory endorsement and country of destination; today it silently gets whatever
   CGST/SGST the user typed, or nothing, with no endorsement.
4. Nothing warns the user. The app is *confidently* wrong, which is worse than being
   incomplete.

### (d) The minimal correct data model

This is deliberately the smallest model that produces legally correct output. **Size: L**
(it is L because it touches the schema, all three invoice shapes, `computeTotals`,
`buildTotalsRows`, both renderings, the API normalizer, and the AI patch contract).

```ts
// --- new invoice-level fields (models/Invoice.ts) ---
supplierStateCode: string        // "29" — 2-digit GST state code. REQUIRED when GST applies.
placeOfSupplyStateCode: string   // "27" — 2-digit code, or "96" for "Other Country"
placeOfSupplyLabel: string       // "Maharashtra" / "United States" — printed on the invoice
supplyKind: "intra" | "inter" | "export" | "sez"   // DERIVED, but stored (audit trail)
exportWithPaymentOfTax?: boolean // only when supplyKind is "export"|"sez"
lutArn?: string                  // printed when exporting without payment of tax
countryOfDestination?: string    // required when supplyKind === "export"
taxTreatment: "gst" | "none" | "composition"  // see §5 — unregistered users pick "none"

// --- per line item ---
taxRatePercent: number           // the FULL rate: 0 | 0.1 | 0.25 | 3 | 5 | 12 | 18 | 28 | 40
// derived per line, stored:
taxableValue: number             // (quantity * price) - lineDiscount
cgstAmount: number               // 0 when inter-state
sgstAmount: number               // 0 when inter-state ("sgst" doubles as UTGST — label switches)
igstAmount: number               // 0 when intra-state
cessAmount?: number              // NICE-TO-HAVE; only sin/luxury goods

// --- invoice-level rollups (replace the two flat fields) ---
totalCgst, totalSgst, totalIgst, totalCess: number
// keep legacy `cgst`/`sgst`/`tax` readable for old rows, exactly as the codebase already
// does with `?? tax` in resolveRecordAmounts.
```

**Derivation logic** — one pure function, in `lib/invoice-domain.ts`, tested like
`lib/numeric-input.ts` is:

```ts
export type SupplyKind = "intra" | "inter" | "export" | "sez";

export function deriveSupplyKind(input: {
  supplierStateCode: string;
  placeOfSupplyStateCode: string;   // "96" == outside India
  recipientIsSez: boolean;
  recipientIsOutsideIndia: boolean;
}): SupplyKind {
  if (input.recipientIsOutsideIndia || input.placeOfSupplyStateCode === "96") return "export";
  if (input.recipientIsSez) return "sez";            // ALWAYS IGST, even same state
  return input.supplierStateCode === input.placeOfSupplyStateCode ? "intra" : "inter";
}

// Union territories WITHOUT a legislature use UTGST in place of SGST.
// Delhi (07), Puducherry (34) and Jammu & Kashmir (01) HAVE legislatures -> SGST.
const UTGST_CODES = new Set(["04","25","26","31","35","38","97"]); // Chandigarh, Daman&Diu/DNH,
// (26 = the merged Dadra & Nagar Haveli and Daman & Diu), Lakshadweep, Andaman & Nicobar,
// Ladakh, Other Territory. Label the second tax column "UTGST" when
// supplyKind === "intra" && UTGST_CODES.has(supplierStateCode).

export function splitLineTax(taxableValue: number, ratePercent: number, kind: SupplyKind) {
  if (kind === "export" || kind === "sez") {
    // zero-rated. If exportWithPaymentOfTax, charge FULL rate as IGST and claim refund.
    return { cgst: 0, sgst: 0, igst: withPayment ? round2(taxableValue * ratePercent / 100) : 0 };
  }
  if (kind === "inter") {
    return { cgst: 0, sgst: 0, igst: round2(taxableValue * ratePercent / 100) };
  }
  const half = round2(taxableValue * (ratePercent / 2) / 100);
  return { cgst: half, sgst: half, igst: 0 };   // note: half is rounded, then doubled
}
```

**The money formula changes** from
`subtotal − discount + cgst + sgst + convenienceCharge`
to
`Σ(line taxable value) − invoiceDiscount + totalCgst + totalSgst + totalIgst + totalCess + convenienceCharge`,
where the tax totals are **sums of per-line derived amounts, never user input**. Keep the
clamp-at-0 and `round2` discipline; keep `computeTotals` as the single formula and make
`buildTotalsRows` emit rows conditionally: `CGST`+`SGST` **or** `CGST`+`UTGST` **or**
`IGST` — never CGST/SGST and IGST together. (Emitting all three with zeros is the wrong
fix: a printed invoice showing "IGST ₹0.00" next to CGST/SGST is a red flag to an auditor.)

**Validation** (extend `validateInvoice`, the one validator):
- `taxTreatment === "gst"` ⇒ `supplierStateCode` and `placeOfSupplyStateCode` required.
- `supplyKind === "inter"` ⇒ `totalCgst === 0 && totalSgst === 0`. Hard error, not a warning.
- `supplyKind === "intra"` ⇒ `totalIgst === 0`.
- `supplyKind === "export"` ⇒ `countryOfDestination` required; if not
  `exportWithPaymentOfTax`, require `lutArn` **and** force the statutory endorsement text
  onto the document; reject any CGST/SGST.
- `billToGstin` present ⇒ its **first two characters must equal** `placeOfSupplyStateCode`
  unless the user has explicitly overridden POS (immovable-property etc.). This one check
  catches most real-world mistakes for free.
- `supplierStateCode` must equal the first two characters of `companyGstin`.

**UX that makes this survivable** (the product principle is "GST is a default, not an
advanced mode"): the user sets their own State **once** (a profile-ish default remembered
from the last invoice — there is no user profile model today, so read it off the most
recent invoice). Then POS auto-fills from the client's GSTIN's first two digits, or from a
State picker for unregistered clients. The CGST/SGST-vs-IGST decision is then **never shown
as a choice** — the invoice just says the right thing, with one line of explanation
("Inter-State supply — IGST applies"). That is the honest reading of "zero-setup speed":
one field, derived everything else.

## 3. Rates, per-line tax, and rounding

### (a) The rate slabs actually in force in 2026 — **the 2025 restructuring did change them**

I verified this because it is the kind of thing a codebase gets wrong for years. The 56th
GST Council (3 Sep 2025) rationalised the slabs, effective **22 September 2025** ("GST 2.0"):

- **12% and 28% are abolished.** ~99% of 12% items moved to **5%**; ~90% of 28% items moved
  to **18%**; luxury/sin goods moved up to a **new 40%** slab.
- Slabs now in force: **0% (nil/exempt), 5%, 18%, 40%.**
- **Special rates survived unchanged: 3%** (gold, silver, platinum, jewellery) and
  **0.25%** (rough diamonds, unworked precious/semi-precious stones).
- **Compensation cess was scrapped** on everything except pan masala, gutkha, cigarettes,
  chewing tobacco/zarda, unmanufactured tobacco and bidi.
- Nil-rated expanded: individual life and health insurance premiums (were 18%), 33
  lifesaving medicines, educational stationery.

For Invoicey's user — a services freelancer — the practical rate is **18%** in almost every
case, occasionally **5%**, and **0%** for exports under LUT. So the rate picker should be
`[0, 5, 18, 40]` with `3` and `0.25` behind an "other rates" affordance. **Do not hardcode
12 or 28** — an app offering those in 2026 is visibly stale, and if a user picks 12% on a
service they have mis-charged.

**UNVERIFIED:** whether any further rate changes were notified between Sep 2025 and Aug 2026.
Treat the slab list as a `lib/gst-rates.ts` constant with a `lastVerified` date comment
rather than as scattered literals, so it can be re-checked cheaply.

### (b) Why per-line rates matter, and one invoice-level amount does not work

Invoicey's model — one CGST number and one SGST number for the whole invoice — breaks for
three ordinary cases:

1. **Mixed-rate invoices.** A designer bills ₹50,000 consulting (18%) and ₹2,000 of printed
   books (0%). One invoice-level amount cannot represent this, and Rule 46(k)/(l) *require*
   the **rate and amount of tax per line**, not a lump sum.
2. **GSTR-1 reporting.** The return is filed rate-wise (`Table 12` HSN summary is rate-wise
   and HSN-wise). An invoice with no per-line rate cannot be transcribed into a return
   without the user redoing the arithmetic by hand — which is exactly the work the product
   claims to remove.
3. **It is user-entered, so it is unverifiable.** The codebase is rigorous about never
   trusting client numbers for the *total* (`normalizePayload` recomputes), yet the tax
   amount itself is a free-typed number. A typo in the CGST box produces a totally
   plausible-looking, arithmetically self-consistent, legally wrong invoice.

The fix is the per-line `taxRatePercent` in §2's model, with amounts **derived**. The
invoice-level `cgst`/`sgst` fields become read-only rollups (and remain readable for legacy
rows through the existing `?? tax` pattern).

### (c) Rounding

**Section 170, CGST Act 2017** — "Rounding off of tax, etc." The amount of tax, interest,
penalty, refund or any other sum payable **shall be rounded off to the nearest rupee**;
₹0.50 and above rounds **up**, below ₹0.50 rounds **down** (normal rounding, not
banker's rounding, not always-up). It applies to **each tax component (CGST, SGST, IGST)
separately**, and **per invoice** — because tax is payable invoice by invoice.

Additionally, conventional practice (not statutory) is a **"Round Off"** line on the invoice
carrying the ±paise difference so the grand total is a whole rupee, which is why nearly
every Indian invoice you have seen has a `Round Off: -0.32` row.

**(b) What Invoicey has.** `round2` everywhere — two decimals, `Number(x.toFixed(2))`. Tax
is never rounded to the rupee. There is no round-off row.

**(c) Gap.** **HIGH** (not a BLOCKER — a 2-decimal tax amount is not an offence, but it
diverges from the return the user will file, and creates paise-level mismatches with the
client's books that generate exactly the email a solo operator does not want).

Watch the ordering trap: the correct sequence is *compute per-line tax at 2dp → sum per
component → round each component to the nearest rupee → total*. Rounding each line to the
rupee and then summing gives a different, wrong answer.

### (d) Implementation sketch — **M**

```ts
// lib/gst-rates.ts
export const GST_RATES = [0, 5, 18, 40] as const;          // GST 2.0, w.e.f. 22-09-2025
export const GST_SPECIAL_RATES = [0.25, 3] as const;       // bullion / rough stones
// lastVerified: 2026-08

// lib/invoice-domain.ts
export const roundToRupee = (v: number) => Math.round(v);  // JS Math.round is half-up: matches s.170
```
- `computeTotals` gains per-line tax computation and per-component rupee rounding.
- `buildTotalsRows` gains an optional `{ label: "Round Off", kind: "line" }` row emitted
  only when the delta is non-zero, so both renderings pick it up for free.
- The editor's %/₹ toggle becomes redundant for tax and should be **removed** — a per-line
  rate is strictly better and the current toggle's percentage is not even persisted.
  Keep the toggle for `discount`, where both modes are genuinely meaningful.
- `tests/` gains a table-driven case set: mixed rates, 18% intra split into two 9% halves
  with the half rounded before doubling, an inter-State 18% IGST, a zero-rated export.

## 4. The other document types Indian users need

Invoicey has **one** document type, hardcoded as `INVOICE`. In real Indian practice a solo
operator issues at least four of the following in a normal year.

### Bill of Supply — CGST **Rule 49**
- **Who/when:** a registered person supplying **exempt** goods/services, **or** a person
  paying tax under the **composition scheme**, issues a *Bill of Supply* **instead of** a
  tax invoice. It carries **no tax** and shows no tax columns.
- **Particulars:** essentially Rule 46 minus the tax fields — supplier name/address/GSTIN,
  16-char serial unique per FY, date, recipient name/address/GSTIN, HSN/SAC, description,
  value of supply, signature.
- **Rule 46A** allows an **"Invoice-cum-Bill of Supply"** when a registered person supplies
  both taxable and exempt goods/services to an **unregistered** person in a single
  transaction.
- Gap: **HIGH**. A composition dealer or an exempt-services supplier literally cannot use
  Invoicey without issuing an illegal document (a "TAX INVOICE" heading with no GSTIN).

### Proforma invoice
- **Not a GST document at all** — no statutory rule governs it. It is a pre-supply quote of
  what the invoice *will* say, and it must **not** be titled "Tax Invoice", must not carry
  an invoice serial from the tax-invoice series, and creates no tax liability and no ITC.
  Convention: title "PROFORMA INVOICE", its own numbering series, a validity date, and the
  line "This is not a tax invoice."
- Gap: **HIGH** — this is arguably the single most-requested missing document for
  freelancers, because it is how they get an advance approved by a client's finance team.

### Quotation / Estimate
- Also non-statutory. Title "QUOTATION" or "ESTIMATE", own series, validity ("valid for
  15 days"), no tax liability, usually shows tax as "GST @18% extra as applicable".
- Gap: **NICE-TO-HAVE** for a services freelancer, **HIGH** for anyone selling goods.

### Delivery Challan — CGST **Rule 55**
- **Who/when:** required whenever a registered person **moves goods for a reason other than
  supply** — job work, goods sent on approval, liquid gas where quantity is unknown at
  dispatch, transport in semi-knocked-down condition, exhibition stock.
- **Particulars:** date and number; consigner name/address/GSTIN; consignee name/address/
  GSTIN; HSN and description; **quantity (provisional where exact quantity is unknown)**;
  **taxable value**; tax rate and amount where the movement is for supply; place of supply
  for inter-State movement; signature. Issued in **triplicate** for goods (Original for
  consignee, Duplicate for transporter, Triplicate for consigner).
- Gap: **NICE-TO-HAVE** for Invoicey's stated services-freelancer user; **BLOCKER** for any
  goods business. Given PRODUCT.md's narrow scope, deferring this is defensible — say so
  explicitly rather than leaving it as an unknown.

### Credit Note — **Section 34(1)**, particulars in **Rule 53**
- **Who/when:** issued by the **supplier** when the taxable value or tax **charged on the
  original invoice exceeds** what is actually payable — i.e. post-supply discount, sales
  return, deficiency in service, or a plain overcharge.
- **Particulars (Rule 53(1A)):** the words **"Credit Note"** prominently; supplier name/
  address/GSTIN; nature of the document; 16-char serial unique for the FY; date; recipient
  name/address/GSTIN (or, if unregistered, name/address + delivery address + State name and
  code); **serial number(s) and date(s) of the corresponding tax invoice(s)**; value of
  supply, rate and amount of tax credited; signature.
- **Hard deadline — this is the bit apps get wrong:** to actually **reduce the supplier's
  output tax liability**, the credit note must be **declared in a return no later than
  30 November following the end of the financial year in which the original supply was
  made, or the date of filing the annual return (GSTR-9) for that year, whichever is
  earlier**. (Moved from "the September return" to 30 November by the Finance Act 2022,
  effective 01-10-2022, from FY 2021-22 onward.) After that date the credit note is a
  purely commercial document and adjusts nothing for GST.
- There is **no time limit on *issuing*** a credit note — only on declaring it. An app
  should therefore show the deadline as a warning, not a hard block.
- Gap: **HIGH**. Today a user who over-billed has no lawful path in Invoicey. Editing the
  original invoice is exactly the wrong answer under GST (and the app *does* allow editing
  a saved invoice, which is a quiet audit hazard once the invoice has been reported).

### Debit Note — **Section 34(3)**, same Rule 53 particulars
- Issued by the supplier when the taxable value or tax **charged is less than** what is
  payable (undercharge, upward price revision). Word **"Debit Note"** prominently.
  A **supplementary invoice** is treated as a debit note.
- **No 30-November deadline** — a debit note increases liability, so the government is
  content to receive it whenever. (The *recipient's* ITC on it is governed by §16(4).)
- Gap: **HIGH**, same as credit note.

### Receipt Voucher — **Rule 50** (advances)
- **Who/when:** §31(3)(d) — on **receipt of an advance payment**, the registered person
  issues a **Receipt Voucher**, not an invoice.
- **Particulars:** supplier name/address/GSTIN; 16-char consecutive serial unique for the
  FY; date; recipient name/address/GSTIN; description of goods/services; **amount of
  advance**; rate and amount of tax (CGST/SGST/IGST/UTGST/cess); **place of supply** with
  State name and code for inter-State; whether tax is payable on reverse charge; signature.
- Rule 50 provisos: if the **rate is not determinable** at the time of receipt, tax is
  charged at **18%**; if the **nature of supply is not determinable**, it is treated as an
  **inter-State supply** (IGST).
- Companion documents: **Rule 51 Refund Voucher** (advance refunded, no supply made) and
  **Rule 52 Payment Voucher** (issued by a recipient paying tax under reverse charge to an
  unregistered supplier).
- **Important 2026 nuance (UNVERIFIED in scope detail):** GST on advances for **services**
  is payable on receipt; for **goods**, advance-receipt GST was withdrawn for all taxpayers
  (Notification 66/2017-CT). So for Invoicey's services-freelancer user, the receipt
  voucher is live and relevant.
- Gap: **HIGH** for anyone who takes a deposit — which is most freelancers.

### (b)/(c)/(d) for the whole section

**What Invoicey has:** nothing. One hardcoded title, one numbering space, no linkage
between documents.

**Gap severity:** **HIGH** overall (not BLOCKER — the tax invoice itself is the blocker;
these are documents the user simply cannot produce at all, so they leave the app for them,
which is the retention risk PRODUCT.md cares about).

**Implementation sketch — M for the first three, L for the full set**

```ts
documentType: "tax_invoice" | "invoice" | "bill_of_supply" | "proforma"
            | "quotation" | "delivery_challan" | "credit_note" | "debit_note"
            | "receipt_voucher"
originalInvoiceRef?: { invoiceId: string; invoiceNumber: string; invoiceDate: Date }
                     // REQUIRED for credit_note / debit_note (Rule 53)
validUntil?: Date    // proforma / quotation
reasonForIssue?: string  // credit/debit note: "post-supply discount", "sales return", ...
```
- One `DOCUMENT_META` map drives: the `<h1>` in `lib/invoice-export.ts` and the JSX
  preview, whether the tax columns render at all (bill of supply: no), whether a
  "not a tax invoice / creates no tax liability" disclaimer prints (proforma, quotation),
  and which numbering series is used.
- **Separate numbering series per document type** is not optional — Rule 46(b)'s "unique
  for a financial year" is per series, and mixing a proforma into the tax-invoice series
  creates a gap in the invoice sequence that an auditor will ask about.
- Credit notes should be created via a **"Create credit note" action on an existing
  invoice**, pre-filling from it and storing `originalInvoiceRef` — not as a blank form.
  Show, non-blockingly, "Declare by 30 Nov {FY+1} to adjust GST".
- A `Credit note` reduces; make the totals rows label the grand total "Total Credited".
- This pairs with the record-retention point in §11: once an invoice has been *issued*, the
  right affordance is a credit/debit note, not an edit. Consider locking edits after a
  `issuedAt` timestamp is set.

## 5. Composition scheme, and the unregistered majority

### (a) Registration thresholds — who even has a GSTIN

Aggregate turnover in a financial year, above which registration becomes mandatory:

| | Normal-category States | Special-category States |
|---|---|---|
| Supplier of **goods** | **₹40 lakh** | **₹20 lakh** |
| Supplier of **services** | **₹20 lakh** | **₹10 lakh** |

Special-category States for this purpose: Arunachal Pradesh, Manipur, Meghalaya, Mizoram,
Nagaland, Sikkim, Tripura, Uttarakhand, Puducherry, Telangana (list varies by notification —
**UNVERIFIED** at the exact current membership; the ₹40L/₹20L headline is well confirmed).
**Assam and Jammu & Kashmir opted for the higher ₹40 lakh limit** despite being
special-category.

Compulsory registration regardless of turnover (§24) still catches some freelancers —
notably anyone making **inter-State taxable supplies of goods**, e-commerce operators, and
persons liable under reverse charge. Note the well-known relief: a **service provider**
making inter-State supplies is exempt from compulsory registration up to the ₹20 lakh
threshold (Notification 10/2017-IT), which is why so many Indian freelancers who bill
across States legitimately have no GSTIN. (**UNVERIFIED** as to whether this notification
is still in force in 2026 — the ₹20L threshold itself is confirmed.)

**The consequence for the product: a large fraction — plausibly the majority — of
Invoicey's target users have no GSTIN at all.**

### (b) What a NON-registered freelancer must issue

- The document is a plain **"Invoice"** or **"Bill"**. It **must not** be headed
  **"Tax Invoice"**, must not show a GSTIN, and must show **no GST line at all**.
- **§32(1) CGST Act — prohibition of unauthorised collection of tax:** "a person who is not
  a registered person **shall not collect** in respect of any supply … any amount by way of
  tax". An unregistered person who nevertheless charges "GST" must pay it over immediately
  with interest under §50 (via §76), and is exposed to penalty under §122. **An app that
  nudges an unregistered user into printing a CGST/SGST line is walking them into an
  offence.**
- What such an invoice does contain, by convention: name, address, contact, PAN (clients
  need it for TDS — see §8), invoice number, date, description, quantity, rate, amount,
  total, amount in words, payment details, and often the line "Not registered under GST"
  or "GST not applicable — turnover below the registration threshold."

**(b) What Invoicey has.** `cgst` and `sgst` are `required: true` in the Mongoose schema
(defaulted to 0), they are permanent rows in `buildTotalsRows`, and they are permanent
fields in the editor. The export always prints **CGST ₹0.00** and **SGST ₹0.00** rows even
when there is no tax. There is no way to say "I am not GST-registered".

**(c) Gap. BLOCKER** — for a different reason than §2, and this one is arguably worse
because it hits *more* users:
1. Every invoice an unregistered freelancer produces carries two zero-value tax rows that
   should not be on the document at all. It looks like a tax invoice from someone with no
   GSTIN, which is the exact shape of a fraudulent invoice.
2. PRODUCT.md's principle 3 ("GST is a default, not an advanced mode") is currently
   implemented as "GST is mandatory and unskippable", which is a different and wrong thing.
   Being *India-first* means handling the unregistered case natively, not treating it as
   an omission.

### (c2) Composition scheme

- **Turnover limits:** ₹1.5 crore for goods (₹75 lakh in specified special-category
  States); **₹50 lakh** for service providers under the §10(2A) composition-like scheme.
  A goods dealer under composition may also supply services up to **₹5 lakh or 10% of
  turnover, whichever is higher**.
- **Rates (tax paid out of pocket, not collected from the customer):** 1% of turnover for
  traders/manufacturers (0.5% CGST + 0.5% SGST), 5% for restaurants (2.5%+2.5%), 6% for the
  §10(2A) service providers (3%+3%). (**UNVERIFIED** whether GST 2.0 altered these — the
  1%/5%/6% structure is what current sources report.)
- **A composition dealer issues a Bill of Supply, never a tax invoice**, and
  **CGST Rule 5(f) requires the words, at the top of the document:**
  **"composition taxable person, not eligible to collect tax on supplies"** — verbatim.
  (Rule 5(g) separately requires a signboard at the place of business; not the app's problem.)
- A composition dealer **cannot** make inter-State outward supplies of goods and cannot
  claim ITC.

**Gap: HIGH.** Small but strictly-worded requirement, cheap to implement, and getting it
wrong is a visible compliance failure.

### (d) Implementation sketch — **S**, and it is the highest value-per-line change in this report

```ts
taxTreatment: "none" | "gst" | "composition"   // default "none" until a GSTIN is entered
```
Derivation and rendering rules, all in one place:
- `taxTreatment === "none"` → document title **"INVOICE"**; **omit the CGST/SGST/IGST rows
  entirely** from `buildTotalsRows` (make the tax rows conditional, not zero-valued);
  hide the tax inputs in the editor; optionally print "GST not applicable."
- `taxTreatment === "gst"` → title **"TAX INVOICE"**; require `companyGstin`; §2's
  derivation applies.
- `taxTreatment === "composition"` → title **"BILL OF SUPPLY"**; print the Rule 5(f)
  sentence verbatim at the top; require `companyGstin`; **forbid any tax rows**;
  block inter-State supply of goods with a validation error.

The single UX move that makes this zero-setup: **one optional GSTIN field on the invoice.**
Empty → `"none"`, and the whole tax apparatus disappears. Filled → `"gst"`, and §2's state
derivation switches on. The user is never asked "are you registered?"; they are asked for
a GSTIN, which they either have or don't. That preserves "nothing between sign-in and the
first invoice" while making the default output **legal** for the unregistered majority,
which it currently is not.

Also: relax `cgst`/`sgst` from `required: true` to genuinely optional in
`models/Invoice.ts`, and make the tax rows in `buildTotalsRows` conditional. Right now the
"zero rows always print" behaviour is baked into the shared totals builder, so fixing it in
one place fixes both the preview and the export — the codebase's existing design pays off here.

## 6. e-Invoicing (IRN/QR) and e-Way Bill

### (a) What the law requires

**e-Invoicing.**
- **Threshold as of 2026: aggregate annual turnover (AATO) ≥ ₹5 crore in any FY since
  2017-18** ⇒ e-invoicing is mandatory for **B2B**, B2G, exports, and SEZ supplies.
  It does **not** apply to B2C. Confirmed unchanged for 2026.
- Mechanics: the seller's software posts the invoice as **JSON in the notified INV-01
  schema** to an **Invoice Registration Portal (IRP)**. The IRP validates it, generates a
  **64-character IRN** (a hash of supplier GSTIN + document type + financial year +
  document number), digitally signs the JSON, and returns a **signed QR code**. The
  **IRN and QR must be printed on the invoice**, and the invoice is not a valid tax
  invoice without them (Rule 48(4)/(5)).
- **30-day reporting window:** taxpayers with **AATO ≥ ₹10 crore** cannot report invoices,
  credit notes or debit notes **older than 30 days** to the IRP — effective **1 April 2025**.
  Past that, the IRP rejects the document and no IRN is generated, which is unfixable.
- Integration routes: (i) **direct API** with the IRP (requires GSTIN-linked API
  credentials, IP whitelisting, and sandbox certification), (ii) via a **GSP/ASP**
  (GST Suvidha Provider — a commercial intermediary, per-document or subscription pricing),
  (iii) manual offline-utility upload on the portal.
- Certain categories are **exempt regardless of turnover**: banks/NBFCs/insurers, GTAs,
  passenger transport, cinema admission, SEZ *units* (developers are not exempt), and
  government departments/local authorities.

**e-Way Bill.**
- Required for the **movement of goods** where the **consignment value exceeds ₹50,000**,
  inter-State or intra-State. **Services do not generate an e-way bill** — there is no
  movement of goods.
- Intra-State thresholds are **State-specific and higher in several States** (Maharashtra,
  Delhi, Punjab, Bihar, Tamil Nadu among them). West Bengal fixed a ₹50,000 intra-State
  threshold effective **1 June 2026**, with intra-State **job-work movement exempt**.
- ~150 notified goods (essentials, perishables) are exempt regardless of value.
- An EWB is generated on the NIC portal (EWB-01: Part A invoice/consignment data,
  Part B vehicle/transporter data) and is validity-limited by distance.

### (b) What Invoicey has

Nothing, and correctly so — there is no IRP client, no GSP relationship, no INV-01 schema,
no QR generation, no digital signature handling.

### (c) The gap, and the honest recommendation

**NICE-TO-HAVE for e-invoicing. Explicitly OUT OF SCOPE for e-way bill.**

This is the one place in this report where I recommend **not building the thing**:

1. **Threshold mismatch with the user.** Invoicey's user, per PRODUCT.md, is a solo
   operator billing "a handful of clients a month". ₹5 crore of turnover is roughly two to
   three orders of magnitude away. A user who crosses ₹5 crore has an accountant and Zoho
   Books, and will not be running their statutory filings through a free side project.
2. **It cannot be free.** Direct IRP integration requires per-GSTIN credentials the
   *user* must issue and manage; the GSP route is a paid commercial contract per document.
   PRODUCT.md commits to "$0, indefinite" with no paid tier. There is no viable funding
   path for a per-invoice external API call.
3. **It is a liability, not a feature.** A failed IRN call means the user's invoice is
   legally invalid and they may not know. That is a fundamentally different risk class from
   "the PDF looked slightly off", and it is not a risk a solo maintainer should absorb.
4. **e-Way bill is even further out of scope** — the product's user sells services;
   services never need one.

**What to build instead — S, and it is genuinely useful:**
- A **field to paste an externally-obtained IRN + signed QR** (`irn?: string`,
  `signedQrPayload?: string`), rendered on the invoice. This lets the rare user who crossed
  the threshold keep using Invoicey for layout while getting the IRN from their accountant
  or the offline utility. The QR is rendered from the signed payload with an **offline** QR
  encoder (see §9 — the same dependency serves the UPI QR).
- A **one-line advisory** in the editor when the user's own entered turnover or invoice
  volume suggests they may be near the threshold. Advisory only; never a blocker.
- Say "Invoicey does not generate IRNs" plainly in the product, the way PRODUCT.md already
  says "Invoicey does not send invoices". Refusing loudly is better than refusing silently.

## 7. GSTIN format and check-digit algorithm (offline-implementable)

### (a) Structure

A GSTIN is **15 characters**, uppercase alphanumeric:

```
 27  AAPFU0939F   1    Z    V
 ^^  ^^^^^^^^^^   ^    ^    ^
 |   |            |    |    +-- 15: Mod-36 check character
 |   |            |    +------- 14: literal 'Z' (reserved; almost always Z)
 |   |            +------------ 13: entity/branch number within the State (1-9, then A-Z)
 |   +-------------------------- 3-12: the holder's 10-character PAN
 +------------------------------ 1-2: GST State code (numeric)
```
PAN itself is `[A-Z]{5}[0-9]{4}[A-Z]` — 4th char is the entity type (`P` individual,
`C` company, `F` firm/LLP, `H` HUF, `T` trust, `A` AOP …), 5th char is the first letter of
the surname/entity name.

**Regex** (format only — must be paired with the checksum, since a regex-valid GSTIN is
trivially forgeable):
```js
const GSTIN_REGEX = /^[0-3][0-9][A-Z]{5}[0-9]{4}[A-Z][1-9A-Z]Z[0-9A-Z]$/;
// Stricter on the state code (rejects 00 and 39-99, allows 01-38):
const GSTIN_REGEX_STRICT =
  /^(0[1-9]|[1-2][0-9]|3[0-8])[A-Z]{5}[0-9]{4}[A-Z][1-9A-Z]Z[0-9A-Z]$/;
```
Note: position 14 is `Z` for ordinary registrations. UIN/OIDAR and a few special
registrations deviate; if you want to accept those, relax position 14 to `[A-Z]` and rely
on the checksum. Recommendation: keep `Z` strict and treat rejection as a warning the user
can override, not a hard block.

### (b) The Mod-36 check-digit algorithm — verified, not assumed

It is **Luhn mod-36** over the alphabet `0-9A-Z` (`0`→0 … `9`→9, `A`→10 … `Z`→35),
computed over the **first 14 characters**, with the multiplication factor **starting at 2
at the rightmost of those 14** and alternating 2,1,2,1…

```ts
const GSTIN_ALPHABET = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZ";

export function gstinCheckDigit(first14: string): string {
  const mod = GSTIN_ALPHABET.length;          // 36
  let factor = 2;
  let sum = 0;
  for (let i = first14.length - 1; i >= 0; i--) {
    const codePoint = GSTIN_ALPHABET.indexOf(first14[i]);
    let digit = factor * codePoint;
    factor = factor === 2 ? 1 : 2;
    digit = Math.floor(digit / mod) + (digit % mod);   // "digit sum" in base 36
    sum += digit;
  }
  return GSTIN_ALPHABET[(mod - (sum % mod)) % mod];
}

export function isValidGstin(value: string): boolean {
  const gstin = (value || "").trim().toUpperCase();
  if (!GSTIN_REGEX_STRICT.test(gstin)) return false;
  return gstinCheckDigit(gstin.slice(0, 14)) === gstin[14];
}
```

**I verified this implementation** by running it against published real GSTINs:
`27AAPFU0939F1ZV`, `29AAGCB7383J1Z4`, `24AAACC1206D1ZM`, `09AAACH7409R1ZZ` — all four
produce the correct check character. The alternate variant (factor starting at 1) fails all
four, which rules it out. The `Math.floor(d/36) + (d%36)` step is essential — dropping it
(i.e. plain `sum += factor*codePoint`) is the most common wrong implementation on the web
and silently accepts invalid GSTINs.

Complexity: zero dependencies, ~15 lines, fully offline, ~microseconds. There is no excuse
for not having it.

## 8. TDS / TCS — what a freelancer actually experiences

### (a) Income-tax TDS: the client deducts, the freelancer gets paid less

This is not the supplier's compliance obligation — it is the **client's** — but it
determines what the freelancer is actually paid, so it belongs on the invoice.

| Section | Applies to | Rate | Threshold (per FY) |
|---|---|---|---|
| **194J** | **Professional** fees (legal, medical, engineering, architectural, accountancy, technical consultancy, interior decoration, advertising; and notified professions incl. most design/IT consulting) | **10%** | **₹50,000** |
| **194J** | **Technical** services (non-professional), and call-centre operators | **2%** | ₹50,000 |
| **194J** | Royalty / non-compete | 10% (2% for certain film royalties) | ₹50,000 |
| **194C** | **Contractor** payments (works contracts, supply of labour, advertising contracts) | **1%** if payee is an individual/HUF, **2%** otherwise | **₹30,000** single payment / **₹1,00,000** aggregate p.a. — one 2026 source reports revised thresholds of ₹2,50,000 aggregate / ₹50,000; **UNVERIFIED**, flag both |
| **206AB / no-PAN** | Payee has not furnished PAN | **20%** | — |

The 194J threshold was raised from ₹30,000 to ₹50,000 (effective FY 2025-26) and is
reported unchanged for FY 2026-27.

**FY 2026-27 renumbering — worth knowing before hardcoding "194J" into UI copy:** under the
new Income-tax Act, the section codes changed for filings from Q1 FY 2026-27 — contractor
payments moved from 194C to **Section 393 SN 6**, professional fees from 194J to
**Section 393 SN 11**. Rates and thresholds are unchanged. **UNVERIFIED** in detail; if you
print a section reference on an invoice, print both ("194J / s.393 SN 11") or print none.

**The invoicing-critical rule: TDS is deducted on the amount *excluding* GST, provided GST
is shown separately on the invoice** (CBDT Circular 23/2017). If the invoice lumps GST into
one figure, the client deducts TDS on the GST too and the freelancer loses cash flow for a
year. This is a concrete, money-affecting reason to show tax as its own line — and an
argument the product can make to the user in one sentence.

### (b) GST TDS/TCS (a different thing with the same name)

- **§51 CGST — GST TDS at 2%** (1% CGST + 1% SGST, or 2% IGST), deducted by government
  departments, PSUs, local authorities and notified persons (incl. metal-scrap buyers) on
  contracts where the **taxable value exceeds ₹2.5 lakh**. Filed in GSTR-7 by the 10th.
- **§52 CGST — GST TCS at 1%** (0.5% CGST + 0.5% SGST intra-State, 1% IGST inter-State),
  collected by **e-commerce operators** on the net value of taxable supplies made through
  them. Filed in GSTR-8 by the 10th. Computed on the **invoice value excluding GST**.
- Both flow to the supplier's **electronic cash ledger** as a credit — they are a
  *receivable*, not an expense.

### (b2) What Invoicey has

Nothing. There is no TDS field, no PAN field, and no "net payable" concept. The invoice
shows a Total, and the user is paid something different.

### (c) Gap — **HIGH**

Two real consequences:
1. **No PAN on the invoice.** Every Indian client deducting TDS needs the payee's PAN;
   without it they must deduct at **20%**. Freelancers routinely get chased by email for
   this. A PAN field is one line of code and removes a recurring friction the user
   experiences on *every* invoice.
2. **No expected-net-payment line.** The user sends an invoice for ₹1,00,000 and receives
   ₹90,000, with no record on the document of why. Every serious Indian invoicing tool
   shows a TDS line.

Not a BLOCKER — TDS is the deductor's legal obligation, not the invoice's — but it is the
gap most likely to be *felt* by the user every single month.

### (d) Implementation sketch — **S**


- `buildTotalsRows` gains, after Total, two informational rows emitted only when
  `tdsSection !== "none"`:
  `{ label: "Less: TDS @10% (194J)", amount: -tdsAmount, kind: "info" }` and
  `{ label: "Net Payable", amount: total - tdsAmount, kind: "grand" }`.
  **Critically: `tdsAmount` must be computed on the pre-GST taxable value, not the total.**
  This needs a new `TotalsRowKind` (`"info"`) so both renderings style it as advisory —

## 9. Payment rails on the invoice

This is the **highest-leverage non-compliance feature in the report**: it makes the invoice
materially better at its actual job (getting the user paid) and it can be built entirely
offline, with no payment gateway, no merchant account, no KYC, no per-transaction cost —
which is the only kind of payments feature compatible with PRODUCT.md's "$0, indefinite,
no paid tier, does not take payments" constraints.

### (a) The UPI deep-link URI (NPCI UPI Linking Specification)

```
upi://pay?pa=<vpa>&pn=<payee name>&am=<amount>&cu=INR&tn=<note>&tr=<ref>
```

| Param | Meaning | Status | Notes |
|---|---|---|---|
| `pa` | **Payee VPA / UPI ID** (`name@bank`) | **Mandatory** | the only truly required field |
| `pn` | **Payee name** | Mandatory in practice | shown in the payer's app |
| `am` | **Amount**, decimal | Mandatory for a *dynamic* QR | omit to let the payer type it |
| `cu` | Currency | Optional | **only `INR` is supported** |
| `tn` | Transaction note | Optional | put the invoice number here |
| `tr` | Transaction reference ID | Conditional (required for merchant txns) | order/bill/booking ID |
| `mc` | Payee merchant category code | Optional | omit for individuals |
| `tid` | Transaction ID | Optional | PSP-generated; omit |
| `mam` | Minimum amount | Conditional | only with an editable-amount rule |
| `url` | Callback/details URL | Optional | could point at a hosted invoice |

**Encoding matters:** every value must be `encodeURIComponent`-ed. `pn` and `tn` with
spaces are the common breakage; `&` or `#` in a company name will silently truncate the
link in some apps. `am` must be a plain decimal string (`"1234.00"`) — **no currency
symbol, no thousands separators**, which means it must *not* go through the existing
`formatCurrency` (that emits `₹1,234.00` and would produce a broken link).

**Static vs dynamic QR:** with `am` present the QR is *dynamic* — the amount is fixed and
the payer just confirms. Without `am` it is *static* and the payer types the amount. For an
invoice you want **dynamic** (amount pre-filled = fewer wrong payments). BharatQR is static
only and also carries card rails; it is not what you want here.

**Generating the QR offline:** a UPI QR is nothing more than the above URI encoded as a
plain QR code. There is no NPCI registration, no API call, and no account required to
*generate* one — the money moves through the payer's own UPI app straight to the VPA.
Any client-side QR encoder produces it. **However**, `lib/invoice-export.ts` builds a raw
self-contained HTML string with a strict escaping discipline and no runtime JS, so the QR
must be rendered to an **SVG path string or a `data:image/png;base64` URI at generation
time** and inlined — not drawn by a script in the exported document. The existing
`toSafeImageUrl` already allowlists `data:`, so a data-URI QR flows through the current
security model unchanged.

### (b) Bank account block

Convention on Indian invoices, printed as a labelled block:
```
Account Name : <beneficiary name as per bank>
Account No.  : <digits>
Bank & Branch: <bank, branch>
IFSC         : <IFSC>
Account Type : Savings / Current
```
**IFSC format:** `^[A-Z]{4}0[A-Z0-9]{6}$` — exactly 11 characters: 4-letter bank code, a
literal **`0`** at position 5 (reserved), then a 6-character branch code. Validate this
offline; there is no checksum, but the format check alone catches most typos. (For a
lookup, `https://ifsc.razorpay.com/<IFSC>` is a free unauthenticated API — optional, and
strictly an enhancement, not a dependency.)

### (c) Payment links

Real hosted payment links (Razorpay/Cashfree/Stripe) require a merchant account, KYC, and
carry per-transaction fees. **Out of scope**, and PRODUCT.md already says the product
"does not take payments". The correct middle ground is a free-text `paymentLinkUrl` the
user pastes in, rendered as both a clickable link and — if you already have the QR encoder
— a second QR. Zero integration, full utility.

### (b2) What Invoicey has

A single free-text `paymentInfo` string, rendered under a "Payment Information" heading as
line-broken text. Nothing structured, no UPI, no QR, no validation.

### (c2) Gap — **HIGH**

Not a legal blocker, but it is the difference between an invoice that looks Indian and one
that looks like a US template with rupees in it. Every Indian invoicing tool has a UPI QR.
For the stated user — a solo operator chasing payment from a handful of clients — a
scannable QR on the PDF is the single most useful thing you can add per line of code.

### (d) Implementation sketch — **M** (S for the fields, M because of the QR encoder)

```ts

bankAccountName?: string;
bankAccountNumber?: string;
bankIfsc?: string;            // /^[A-Z]{4}0[A-Z0-9]{6}$/
bankName?: string;
paymentLinkUrl?: string;      // http/https only, reuse the toSafeImageUrl allowlist idea
```
```ts
// lib/upi.ts
export const buildUpiUri = (o: {
  vpa: string; payeeName: string; amount: number; note?: string; ref?: string;
}) => {
  const q = new URLSearchParams();
  q.set("pa", o.vpa);
  q.set("pn", o.payeeName);
  q.set("am", o.amount.toFixed(2));   // NOT formatCurrency
  q.set("cu", "INR");
  if (o.note) q.set("tn", o.note.slice(0, 50));
  if (o.ref)  q.set("tr", o.ref);
  return `upi://pay?${q.toString()}`;
};
```
- Guard: only emit the UPI block when `currency === "INR"` — `cu` supports INR only, and a
  UPI QR on a USD invoice is a bug.
- The QR encoder is the only new dependency in this entire report. Pick a small,
  dependency-free one that can emit an SVG string server-side/at export time. It pays for
  itself twice: UPI QR here, and the signed e-invoice QR from §6.
- Test the URI builder in `tests/` the way `lib/numeric-input.ts` is tested — pure function,
  encoding edge cases (`&`, `#`, spaces, unicode company names), amount formatting.

## 10. Formatting conventions

### 10.1 Indian digit grouping (lakh / crore)

**Requirement/convention:** Indian numbers group as **2,2,3 from the right** —
`₹1,23,45,678.90`, not `₹12,345,678.90`. Reading "12,345,678" on an Indian invoice makes
the document read as foreign, and an Indian reader has to count digits to parse it.

**What Invoicey has:** `formatCurrency` (`lib/invoices.ts:249`) already does this correctly
— it uses `en-IN` when `currency === "INR"`. **I verified the runtime output:**
`Intl.NumberFormat("en-IN", {style:"currency",currency:"INR"}).format(12345678.9)`
→ `₹1,23,45,678.90`. Correct.

**Gap:** none for currency. **NICE-TO-HAVE:** bare quantities and unit prices in the export
table are interpolated as raw `${item.quantity}` / `formatCurrency(item.price)`; quantity
is unformatted, which is fine, but nothing else in the app formats plain numbers. No action
needed.

One real bug-adjacent note: the `en-IN` locale is selected **only for INR**; other
currencies fall to `en-US`. That is a defensible choice (a USD invoice grouping in lakhs
would be wrong), so leave it.

### 10.2 Amount in words, Indian style

**Convention:** Indian invoices almost universally print the total in words —
`"Rupees One Lakh Twenty Three Thousand Four Hundred Fifty Six and Seventy Eight Paise
Only"`. It is **not** a Rule 46 requirement (I checked — it is absent from the clause list),
but its absence is conspicuous; it is the single most commonly remarked-on omission when an
Indian accountant looks at a foreign-built invoice. It also serves a real anti-tampering
purpose.

Rules that matter: the scale is **thousand / lakh (10⁵) / crore (10⁷)** — never million or
billion; the word **"Only"** terminates it; paise are named ("and Fifty Paise Only") or the
amount is rounded to the rupee and simply ends "Only"; the string is conventionally
capitalised Title Case and prefixed **"Rupees"** (or "US Dollars" etc. for other currencies).

**What Invoicey has:** nothing.

**Gap: HIGH** — cheap, visible, and it is a genuine "looks Indian" signal for a product
whose stated positioning is India-first.

**Implementation — S.** Pure function, no dependency, ~40 lines, testable:
```ts
// lib/amount-in-words.ts
export const amountInWords = (value: number, currency = "INR"): string
// decompose: crore = floor(n/1e7), lakh = floor(n%1e7/1e5),
//            thousand = floor(n%1e5/1e3), hundred = floor(n%1e3/100), rest = n%100
// rest uses a 0-19 table + tens table (Indian English uses "Nineteen", not "Nine-teen")
// paise = round((value - floor(value)) * 100)
```
Render as a full-width row under the totals block in **both** renderings. Because
`buildTotalsRows` is the shared contract, the cleanest insertion is a sibling
`buildTotalsFooter(amounts, currency)` returning the words string, so the two renderings
still cannot drift.

### 10.3 Date conventions

**Convention:** India writes **DD/MM/YYYY** or `DD-MMM-YYYY`. `MM/DD/YYYY` is not merely
unusual — it is **ambiguous and dangerous**: `03/04/2026` means 3 April to an Indian reader
and 4 March to the format Invoicey emits. Invoice date and due date are legally operative
dates (they set the tax period and the payment term).

**What Invoicey has:** `formatDateLong` (`lib/invoices.ts:262`) hardcodes **`en-US`**,
producing `Aug 17, 2026`. Verified at runtime. This is used in the export header, the CSV,
and the footer.

**Gap: HIGH.** `Aug 17, 2026` is not *ambiguous* (the month is spelled), so it is not a
BLOCKER — but it is unmistakably a US-format date on an India-first product, and the
comma-form is not what any Indian invoice uses.

**Implementation — S.** One-line change plus a decision:
```ts
return date.toLocaleDateString("en-GB", { year: "numeric", month: "short", day: "2-digit" });
// -> "17 Aug 2026"   (verified at runtime)
```
`en-GB` short-month is the safest default: unambiguous to every reader, and matches Indian
convention. Do **not** switch to numeric `DD/MM/YYYY` for a document that may cross borders.
Same change applies to the CSV export, where dates should arguably be **ISO `YYYY-MM-DD`**
instead, since a CSV is machine-destined and Excel will re-interpret `17 Aug 2026`
unpredictably by locale.

### 10.4 The April–March financial year and invoice numbering

**Requirement:** Rule 46(b)'s serial number must be **unique for a financial year**, and the
Indian financial year runs **1 April – 31 March**. So the *legal reset point* for numbering
is 1 April, not 1 January. Standard practice is to encode the FY into the number:
`INV/2026-27/001`, `26-27/0042`, `FY2627-001`. Note the 16-character ceiling from §1 —
`INV/2026-27/001` is 15 characters and only just fits; `INVOICE/2026-27/0001` is 20 and is
**illegal**. This is a real trap for a "smart numbering" feature.

Related FY-anchored dates the app could surface: GSTR-1 monthly (11th) / quarterly, GSTR-3B
(20th), the **30 November** credit-note deadline from §4, the annual return GSTR-9
(31 December), and the LUT renewal at the start of each FY (§2).

**What Invoicey has:** `invoiceNumber` is a required free-text string with **no
uniqueness constraint** (no unique index on `{userId, invoiceNumber}` in
`models/Invoice.ts` — I checked; the only indexes are the three listed there), no length
limit, no charset restriction, no auto-increment, and no FY awareness.

**Gap: BLOCKER**, and it is the quietest one in this report. Rule 46(b) requires a
**consecutive** serial unique per FY. Today a user can save two invoices with the same
number, or a number of 200 characters, or `INV #1`, and the app will accept all three. A
duplicate invoice number is a genuine GST offence and a guaranteed audit finding.

**Implementation — M:**
1. **Uniqueness.** Add a partial unique index:
   `{ userId: 1, financialYear: 1, documentType: 1, invoiceNumber: 1 }`, unique, partial on
   `{ is_deleted: { $ne: true } }`. Handle the E11000 duplicate-key error in the route as a
   409 with a human message — do not let it surface as a 500. Because deletion is soft
   (§11), the partial filter is what lets a number be reused after a soft delete, which is
   probably what a user expects; decide deliberately, and note that GST says a *cancelled*
   invoice number must not be reused, so the safer choice is a **full** unique index that
   includes soft-deleted rows.
2. **Derived FY field.** `financialYear: string` (`"2026-27"`), derived from `invoiceDate`:
   `const fyStart = d.getMonth() >= 3 ? d.getFullYear() : d.getFullYear() - 1;`
   (`getMonth() >= 3` is April onwards). Store it — it is what the unique index and every
   future report keys on.
3. **Charset/length validation** in `validateInvoice`, per §1.
4. **Auto-suggest the next number** on create: read the user's highest number in the
   current FY matching a recognisable pattern and increment. This is the "zero-setup"
   move — the user never types an invoice number again, and cannot create a duplicate or
   a gap. **Warn on gaps**, since a gap in a consecutive series is an audit question.

## 11. Record retention, and soft delete

### (a) What the law requires

**Section 36, CGST Act 2017** — Period of retention of accounts. Every registered person
must retain the books of account and other records required under §35 until the expiry of
**72 months (six years) from the due date of furnishing the annual return** for the year
they relate to. Because the GSTR-9 due date is 31 December following the FY, the practical
horizon is closer to **~6 years 9 months from the start of the financial year**.

Extended retention: where the registered person is a party to an **appeal, revision, or any
other proceeding** before any authority/tribunal/court, or is under **investigation**, the
records must be retained for **one year after the final disposal** of that matter, **or**
the 72-month period, **whichever is later**.

Records may be kept **electronically**; §35/Rule 56–57 require that electronic records be
authenticated, backed up, and **producible in a legible form on demand**, with the relevant
access credentials made available. Related: the Income-tax Act's own retention norm is
generally 6 years from the end of the assessment year (8 years in some reassessment cases)
— so **6–8 years is the honest planning horizon**, not 6.

### (b) What Invoicey has

An unusually good starting position, by accident of design:
- **Nothing is ever hard-deleted.** Every read filters `is_deleted: { $ne: true }`; deletion
  is a `PATCH` with `action: "soft_delete"`. This is exactly the behaviour §36 wants.
- The migration scripts **preserve legacy fields rather than dropping them**
  (`providerId`→`providerIds`, `tax`→`cgst`/`sgst`), so historical documents remain
  reconstructible in the shape they were issued in. Again, accidentally correct.
- Export exists in four formats including JSON, so a user *can* get their data out.

### (c) The gaps

1. **No stated retention guarantee, and a real tension with the product.** PRODUCT.md
   commits to "$0, indefinite" with a Buy-Me-a-Coffee monetisation surface. A user is
   legally obliged to produce these invoices for 6+ years. If the service disappears — the
   realistic outcome for a solo side project — the user is non-compliant. **HIGH**, and it
   is a *product-honesty* issue, not a code issue.
   → **Mitigation, S:** a **bulk export** (all invoices, JSON + CSV, one click), plus a plain
   sentence in the product: "Invoicey is not your system of record. Export your invoices
   each year; GST requires you to keep them for 6 years." That is exactly the register
   PRODUCT.md's voice section asks for, and it converts a liability into a trust signal.
2. **Soft-delete is invisible and irreversible-in-practice.** There is no trash view, no
   restore, and no list of soft-deleted invoices. So the retained data exists but the user
   cannot reach it — which satisfies neither the letter (produce on demand) nor the spirit.
   **HIGH.** → **S:** a "Deleted" filter on the list, plus a restore action (flip
   `is_deleted`), plus include soft-deleted rows in the bulk export, clearly marked.
3. **A "deleted" invoice number vanishes from the sequence.** Under GST an invoice that is
   cancelled must still be accounted for (reported as cancelled, and the number not reused).
   Today a soft-deleted invoice silently leaves a hole in the series with no record of why.
   **HIGH.** → **S:** replace `soft_delete` with a **`cancel`** action that sets
   `status: "cancelled"` and `cancelledAt`/`cancellationReason`, keeps the row visible in
   the list (struck through), and keeps the number reserved. Retain `soft_delete` only for
   genuine drafts that were never issued.
4. **Editing an issued invoice is unrestricted.** `PUT ?id=` updates any invoice at any
   time. Under GST, once an invoice has been issued and reported, corrections happen via a
   credit/debit note (§4), not by mutating history. **HIGH.** → **M:** add
   `issuedAt?: Date`; once set, `PUT` refuses field changes to the money/party/date fields
   and the UI offers "Create credit note" instead. Keep drafts freely editable.
5. **No immutability or audit trail.** Rule 56 wants electronic records to be reliable.
   A minimal, cheap answer: an append-only `revisions: [{at, changedFields}]` array, or at
   minimum an `updatedAt` (the schema has `createdAt` but **no `updatedAt`** — I checked).
   **NICE-TO-HAVE.**

### (d) Implementation summary — **S** for 1–3, **M** for 4

```ts
status: "draft" | "sent" | "paid" | "overdue" | "cancelled"   // + cancelled
issuedAt?: Date;            // set on first "send"/export; locks the money fields
cancelledAt?: Date;
cancellationReason?: string;
updatedAt: Date;            // { timestamps: true } on the schema
financialYear: string;      // from §10.4 — also the natural key for a per-FY export
```
Plus `GET /api/invoices?export=all` returning every invoice (including soft-deleted and
cancelled, flagged) as JSON, and a "Download all my invoices" button.

## 12. Consolidated severity register

### BLOCKERS — the invoice is legally wrong or unusable

| # | Blocker | Why it is fatal | Fix | Size |
|---|---|---|---|---|
| **B1** | **No IGST, no supplier State, no place of supply** (§2) | Every **inter-State** invoice is legally wrong. The recipient cannot claim ITC; the supplier's GSTR-1/3B is misstated. This is the *majority* case for a solo consultant with nationwide clients. | `supplierStateCode`, `placeOfSupplyStateCode`, `supplyKind` + `deriveSupplyKind()` + `splitLineTax()`; conditional CGST/SGST‑vs‑IGST rows | **L** |
| **B2** | **No GSTIN fields** (supplier or recipient) (§1, §7) | Rule 46(a)/(d). Without the supplier's GSTIN the document is not a tax invoice at all; without the recipient's, the client cannot claim ITC. Also blocks B1's derivation. | `companyGstin`, `billToGstin` + `lib/gstin.ts` (regex + verified mod-36 checksum) | **S** |
| **B3** | **Tax is forced on unregistered users** (§5) | `cgst`/`sgst` are `required` and always render as ₹0.00 rows. An unregistered freelancer — plausibly the *majority* of target users — cannot produce a lawful plain invoice, and §32 CGST prohibits an unregistered person collecting tax at all. | `taxTreatment: "none"\|"gst"\|"composition"`; make tax rows in `buildTotalsRows` conditional; document title driven by type | **S** |
| **B4** | **No HSN/SAC, no unit, no per-line tax rate** (§1, §3) | Rule 46(f)/(h)/(k)/(l) require them per line. Also makes mixed-rate invoices impossible and GSTR-1 untranscribable. | Extend the line item across all three invoice shapes + `normalizeItems` | **M** |
| **B5** | **Invoice number: not unique, not length-limited, not charset-limited, not FY-scoped** (§1, §10.4) | Rule 46(b): ≤16 chars, only `A-Z a-z 0-9 - /`, **consecutive and unique per financial year**. The app currently accepts duplicates and 200-char numbers. Duplicate numbering is an audit finding. | Regex in `validateInvoice`; `financialYear` derived field; unique compound index + 409 handling; auto-suggest next number | **M** |
| **B6** | **No place-of-supply / export handling for foreign invoices** (§2) | PRODUCT.md ships USD/EUR/GBP/AED. An export of services must be **zero-rated** with the verbatim Rule 46 endorsement, country of destination, and (if under LUT) the LUT ARN. Today it silently gets whatever the user typed. | Part of B1: `supplyKind: "export"`, `countryOfDestination`, `lutArn`, endorsement text block | **M** (given B1) |

### HIGH

- **H1** Rounding is 2-decimal, not per-component to the nearest rupee (§172 CGST §170); no Round Off row. **M**
- **H2** Rate slabs are absent entirely; when added, must be **0/5/18/40** (+3, 0.25) — **12% and 28% no longer exist** since 22 Sep 2025. **S**
- **H3** No credit note / debit note (§34, Rule 53) — no lawful way to correct an issued invoice; the app instead lets you edit it, which is worse. **M**
- **H4** No bill of supply (Rule 49) / composition Rule 5(f) wording. **S–M**
- **H5** No proforma invoice or quotation — the most-requested missing document for freelancers. **M**
- **H6** No receipt voucher for advances (Rule 50). **M**
- **H7** No PAN field; no TDS line / net-payable (§8). Clients must otherwise deduct at 20%. **S**
- **H8** No UPI VPA / UPI QR / structured bank block (§9) — the biggest "gets you paid" gap. **M**
- **H9** No amount in words, Indian-style (§10.2). **S**
- **H10** Dates render in **`en-US`** (`Aug 17, 2026`) on an India-first product (§10.3). **S**
- **H11** Soft-deleted invoices are unreachable (no trash/restore); cancelled numbers vanish from the series; issued invoices are freely editable (§11). **S–M**
- **H12** No bulk export / no stated retention position, against a 6-year (72-month) legal obligation and a solo-maintained free service (§11). **S**

### NICE-TO-HAVE

- Delivery challan (Rule 55) — only matters if the product ever serves goods businesses.
- A paste-in field for an externally-obtained IRN + signed QR (§6).
- Cess (only sin/luxury goods).
- Reverse-charge indicator as a printed Yes/No (Rule 46(o)) — cheap; arguably HIGH if any user supplies to a body corporate under RCM.
- Signature block / signature image; "computer-generated invoice" line.
- `updatedAt` and a lightweight revision trail.

### Explicitly recommended AGAINST building

- **e-Invoicing / IRN generation** (§6) — ₹5 crore threshold is 2–3 orders of magnitude
  from the target user, it cannot be free, and a failed IRN silently invalidates the user's
  invoice. Refuse loudly instead.
- **e-Way bill** (§6) — services never need one.
- **Hosted payment links / gateway** (§9) — requires KYC, a merchant account, and per-txn
  fees; contradicts PRODUCT.md. Offer a pasted link + offline UPI QR instead.

### Suggested sequencing

The dependency order is real: **B2 → B3 → B1/B6 → B4 → B5**, because the GSTIN field is what
lets the app derive registration status *and* supplier State, and `taxTreatment` is what
lets the tax rows become conditional before you add a third tax to them.

A defensible first release: **B2 + B3 + B5 + H9 + H10 + H7** — all **S**, no new
dependencies, and together they take the app from "produces an unlawful document for both
registered and unregistered users" to "produces a correct plain invoice for the unregistered
majority, and a well-formed one for the rest". **B1** is the large one and is the true
correctness fix; it should follow immediately, not eventually.

### Cross-cutting note on where these changes land

The codebase's existing discipline pays off unusually well here, and the plan should lean on
it rather than route around it:
- `computeTotals` / `buildTotalsRows` in `lib/invoice-domain.ts` are the single choke point
  for the money formula and the printed totals — every tax change in this report is one edit
  there plus conditional rows, and both renderings follow automatically.
- `validateInvoice` is the single validator shared by `InvoiceEditor.saveInvoice` and the
  API — every validation rule above goes in one function.
- The three invoice shapes (`InvoiceRecord` / `InvoiceFormState` / `InvoicePayload`) and
  their mappers in `lib/invoices.ts` mean **every** new field is a four-place edit
  (model, three shapes) plus `normalizeItems`/`normalizePayload` in
  `app/api/invoices/route.ts` — budget for that, it is the main cost driver of the M/L items.
- The AI assistant's field set must stay identical across `prompt.ts`, `contracts.ts`,
  `normalization.ts`, and `apply-patch.ts`. A GSTIN or an HSN code coming from a model is
  untrusted input and must be checksum/format-validated in `normalization.ts`, not merely
  copied through.
- `lib/invoice-export.ts` is a raw HTML string: every new field must be wrapped in
  `escapeHtml` / `toLineBreaks` / `toSafeImageUrl`, and every new CSV cell in
  `neutralizeCsvValue`.
